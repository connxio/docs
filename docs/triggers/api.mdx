## Retry

Implement proper retry logic on the client side when using the Connxio API, or use the [Interaction NuGet](../interaction/nuget/connxio-api.md) which provides built-in retry functionality.

## Custom headers

Add HTTP headers starting with `cx-` to the request you send to the Connxio Messaging API. Connxio copies these headers into the message metadata's `PreDefinedUserProperties` object, making them available to subsequent actions without changing the message body.

For example, send this header to pass a customer ID:

```http
cx-CustomerId: 12345
```

The resulting `PreDefinedUserProperties` object contains:

```json
{
  "cx-CustomerId": "12345"
}
```

The `cx-` prefix remains part of the property name, and the value is stored as a string. Add more `cx-` headers to pass other values, such as an order ID or source system.

## Synchronous communication

Enable **Use synchronous communication** on the API trigger when the caller needs to wait for processing to finish and use the result.

### Response and limitations

Connxio returns one response object per subintegration. Each object contains a `synchronousMessageResponses` entry for every outbound operation, including any messages created by splitting. For example, 10 split messages sent to 3 outbound actions produce 30 entries for that subintegration.

Each entry includes metadata and can include processing error fields such as `errorMessage`, `messageErrorCode`, and `stackTrace`. For [REST actions](../actions/http.md), the endpoint response is available in `metaData.outboundRestResponse`.

Keep these limitations in mind:

- Connxio's resending functionality is unavailable, and pipeline logging is limited. Use the returned error details for troubleshooting.
- Batching actions and the `/batch` endpoint are not supported.
- The caller must handle retries (see [Retry](#retry)).

### Customizing the response

Use a [Script component](../actions/script.md) or [Code component](../integrations/code-components.md) to remap the synchronous API response.

#### Script action

The default script reads the response from `event.content` and returns a flat list of interchange IDs, with one entry per outbound operation:

```js
/**
 * Handler that will be called during the execution of the script.
 *
 * @param {TransformationEvent} event - Contains the file content and metadata about the file.
 * @returns {TransformationEvent} Return the modified event.
 */
const execute = (event) => {
  // Example modification:
  const transformedResponses = [];
  const responses = JSON.parse(event.content);
  for (const response of responses) {
    for (const syncResponse of response.synchronousMessageResponses) {
      transformedResponses.push({
        interchangeId: syncResponse.metaData.interchangeId,
      });
    }
  }
  event.content = JSON.stringify(transformedResponses);
  return event;
};
```

For the example response above, the script returns:

```json
[
  { "interchangeId": "00000000-0000-0000-0000-000000000000" },
  { "interchangeId": "11111111-1111-1111-1111-111111111111" }
]
```

Change the fields added to `transformedResponses` to return the data your caller needs.

#### Code component

In a Code component, deserialize `TransformationContext.Content` as `IEnumerable<FinalSynchronousMessageResponse>` using the types from the `Connxio.Transformation` NuGet package:

- `FinalSynchronousMessageResponse` contains `SubIntegrationName`, `TotalResponses`, and `SynchronousMessageResponses`.
- Each `SynchronousMessageResponse` contains `MetaData`, `ErrorMessage`, `MessageErrorCode`, `StackTrace`, `TransientError`, and `Origin`.

Set `TransformationContext.Content` to the serialized output you want the API to return. To change the failure status code, see [Using FailureReturnStatusCode](../integrations/code-components.md#using-failurereturnstatuscode).

### Using the Interaction NuGet

The [Interaction NuGet](../interaction/nuget/connxio-api.md) provides C#/.NET helpers for wrapping and sending messages and reading synchronous responses. Its `errors` field reports client communication errors and is specific to the NuGet; processing errors are returned in the individual response entries.
