# IntegrationConfig model

`IntegrationConfig` describes an integration: how messages arrive, which steps process them, and which settings apply across the flow. The visual editor represents its triggers and actions on the canvas; Code view exposes the configuration behind that flow.

This page explains the model used by Connxio. For a walkthrough of the editor, see [Getting started](./getting-started.md). For an existing integration, see [Move to action based integrations](./move-to-actions.md).

Examples use camelCase JSON names, such as `outputFormat`. The corresponding .NET properties use PascalCase, such as `OutputFormat`. The tables describe model fields, rather than the required fields of a particular API request.

## Two configuration styles

The model supports both action based and legacy integrations:

| Style   | Main fields                            | Flow structure                                                                             |
| ------- | -------------------------------------- | ------------------------------------------------------------------------------------------ |
| Actions | `triggers`, `actions`                  | Triggers receive messages; actions connect through `runAfter` dependencies.                |
| Legacy  | `inboundConnection`, `subIntegrations` | An inbound connection feeds subintegrations with transformations and outbound connections. |

The .NET helper `IsActionBased` returns `true` when **either `Triggers` or `Actions` is non-null**. Empty arrays and dictionaries still count. This helper is not serialized into JSON and does not validate whether the flow is complete.

When working with a legacy configuration, leave `triggers` and `actions` absent or null. Adding empty collections changes how the configuration is classified.

## Example: a small action flow

This excerpt receives a JSON message through an API trigger, prettifies it, and then discards it. It demonstrates the model structure; it omits ownership and other settings needed when creating a complete integration.

```json
{
  "name": "Format incoming JSON",
  "enabled": true,
  "triggers": [
    {
      "id": "receive-message",
      "name": "Receive message",
      "type": "Api",
      "enabled": true,
      "inputFormat": "json",
      "inputEncoding": "utf-8",
      "properties": {
        "useSynchronousCommunication": false
      }
    }
  ],
  "actions": {
    "format-message": {
      "id": "format-message",
      "name": "Format message",
      "type": "PrettifyFormat",
      "enabled": true,
      "runAfter": {},
      "properties": {
        "enabled": true
      }
    },
    "finish": {
      "id": "finish",
      "name": "Finish",
      "type": "Discard",
      "enabled": true,
      "runAfter": {
        "format-message": ["Succeeded"]
      },
      "properties": {}
    }
  }
}
```

The trigger is stored in a list. Actions are stored in a dictionary, where each key matches the action's `id`. `format-message` has no dependencies, so it is an entry action. `finish` runs after `format-message` succeeds.

Trigger IDs identify the message source; they are not predecessor action IDs in `runAfter`. A fresh message starts at the top-level entry actions.

## Integration identity and shared settings

| Field                                | Model type               | Purpose                                                                               |
| ------------------------------------ | ------------------------ | ------------------------------------------------------------------------------------- |
| `id`                                 | String                   | Identifies the integration.                                                           |
| `name`                               | String                   | The integration's display name.                                                       |
| `description`                        | Optional string          | Explains what the integration does.                                                   |
| `enabled`                            | Boolean                  | Controls whether the integration is active.                                           |
| `archived`                           | Boolean                  | Records whether the integration is archived.                                          |
| `tags`                               | Optional list of strings | Labels used to organize integrations.                                                 |
| `sender`, `receiver`                 | Optional strings         | Identify the systems involved for logging.                                            |
| `companyId`, `companyName`           | Strings; name optional   | Company ownership.                                                                    |
| `subscriptionId`, `subscriptionName` | Strings; name optional   | Subscription ownership.                                                               |
| `environment`                        | `Environment` enum       | Internal deployment environment (`Green` or `Blue`).                                  |
| `loggingWebhooks`                    | Optional collection      | External logging destinations and settings. See [Logging](./logging.md).              |
| `retryOptions`                       | Optional object          | Retry and backoff settings, including inbound retry options. See [Retry](./retry.md). |

## Triggers

`triggers` contains `CxTrigger` objects. Each defines an incoming message source and its input settings. Available operations and connection settings are described in the [trigger reference](../triggers/index.mdx).

Triggers and actions share these fields:

| Field              | Purpose                                              |
| ------------------ | ---------------------------------------------------- |
| `id`               | Identifies this trigger or action.                   |
| `name`             | Human-readable name shown in the editor and logs.    |
| `type`             | Selects the operation and the shape of `properties`. |
| `enabled`          | Enables or disables the trigger or action.           |
| `subAction`        | Optional operation variant, where supported.         |
| `properties`       | Settings specific to the selected operation.         |
| `loggingOverrides` | Optional overrides for logging settings.             |

A trigger adds the following fields:

| Field                | Purpose                                                                                        |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| `inputFormat`        | Format of incoming content, such as `json` or `xml`.                                           |
| `inputEncoding`      | Character encoding of incoming content.                                                        |
| `removeBom`          | Optional setting for removing a byte order mark.                                               |
| `intervalExpression` | Schedule expression for triggers that use a schedule.                                          |
| `wrapperType`        | Selects how wrapped incoming messages are handled. See [Wrappers](../interaction/wrappers.md). |

When a trigger's input format or encoding is unset, the model's lookup helpers fall back to the integration's `messageInboundFormat` or `messageInboundEncoding`.

## Actions

`actions` contains `CxAction` objects keyed by action ID. Actions share the common fields above and add processing and connection settings:

| Field                       | Purpose                                                                                                         |
| --------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `runAfter`                  | Maps preceding action IDs to accepted outcomes. An empty dictionary makes the action an entry within its scope. |
| `condition`                 | Optional CxMaL expression evaluated before execution. A false condition skips the action.                       |
| `outputFormat`              | Output format setting for the action.                                                                           |
| `outputEncoding`            | Output encoding setting, used by operations that write or send content.                                         |
| `scopeId`                   | ID of the containing Scope action, or null for a top-level action.                                              |
| `scopeBranch`               | Optional branch grouping used when finding sibling actions. It does not enable parallel scope entries.          |
| `ackOptions`                | Acknowledgment settings where supported.                                                                        |
| `intervalOptions`           | Interval settings where supported.                                                                              |
| `continuousBatchOptions`    | Continuous batching settings where supported.                                                                   |
| `duplicateDetectionOptions` | Duplicate detection settings where supported.                                                                   |

`properties` is not the same shape for every action. For example, `Api` uses API connection properties, `Script` uses inline script properties, and `Scope` uses scope properties. The type resolver also considers `subAction` for operations with variants.

Model type names can differ from editor labels: **HTTP** uses `REST`, **Azure Blob** uses `AzureStorageBlob`, and **Prettify** uses `PrettifyFormat`. Use the [action reference](../actions/index.mdx) for each operation's settings. An enum value's presence in the model does not guarantee that the execution engine supports it.

### Execution order and outcomes

The order of entries in `actions` does not set execution order. `runAfter` connects actions using these outcomes:

- `Succeeded`: the preceding action completed successfully.
- `Failed`: execution was routed to a failure path.
- `Skipped`: the preceding action was disabled, its condition was false, or it produced a termination outcome.

A successor can accept several outcomes from one predecessor:

```json
"runAfter": {
  "format-message": ["Succeeded", "Skipped"]
}
```

If several actions are eligible after a step, processing branches. Each branch starts with the content at that point and continues independently. The current engine does not collect parallel branch outcomes into a shared join, so do not use multiple predecessor IDs to build a step that waits for both branches.

A destination must be represented by an explicit action. Reaching the end of a transformation path does not automatically send its content to an outbound connection.

### Scopes and inherited settings

A Scope is an action with `type: "Scope"`. Its children remain in the same `actions` dictionary and reference it through `scopeId`. Dependencies inside the scope connect sibling actions; the scope's own successors describe what runs after the group finishes.

Format and encoding lookup checks the action's own setting first, then its ancestor scopes, then trigger settings. Logging overrides follow the scope hierarchy too: for each logging field, the nearest enabled override takes precedence.

Scope properties can include `predefinedUserProperties`, which are available to actions inside the scope. See [Scope](../actions/scope.md) for their lifetime and current limitations, including the requirement for a single entry chain.

## Legacy configuration fields

Legacy integrations use `inboundConnection` and `subIntegrations` to describe their processing paths.

| Field                                            | Purpose                                                                           |
| ------------------------------------------------ | --------------------------------------------------------------------------------- |
| `inboundConnection`                              | Adapter settings for the incoming connection.                                     |
| `subIntegrations`                                | The processing paths, each with its own transformations and outbound connections. |
| `messageInboundFormat`, `messageInboundEncoding` | Integration-level input settings; also used as fallbacks by trigger helpers.      |
| `pollingIntervalInSeconds`, `intervalExpression` | Integration-level scheduling settings.                                            |
| `removeBom`                                      | Integration-level byte order mark setting.                                        |
| `handleAsBinaryFile`                             | Binary file handling flag; defaults to `false` in the model.                      |

Each `SubIntegration` contains:

| Field                                              | Purpose                                                  |
| -------------------------------------------------- | -------------------------------------------------------- |
| `subIntegrationId`, `subintegrationName`           | Identity and optional display name.                      |
| `enabled`, `condition`                             | Whether the path runs and its optional condition object. |
| `transformations`                                  | Ordered transformation steps.                            |
| `outboundConnections`                              | Destination connection settings.                         |
| `preDefinedUserProperties`                         | User defined properties for the path.                    |
| `messageOutboundFormat`, `messageOutboundEncoding` | Output settings.                                         |
| `sender`, `receiver`, `loggingWebhookOverrides`    | Logging identity and overrides for this path.            |

The legacy `condition` is a condition object; an action's `condition` is an expression string. Moving a configuration to actions involves translating its structure and behavior, rather than just renaming fields. Follow the [migration guide](./move-to-actions.md).

## Audit, storage, and compatibility fields

These fields describe the saved configuration and its history:

| Field                       | Purpose                            |
| --------------------------- | ---------------------------------- |
| `createdBy`, `createdAtUtc` | Creator and creation time.         |
| `updatedBy`, `updatedAtUtc` | Last editor and update time.       |
| `cosmosEntityName`          | Computed storage entity type name. |
| `_etag`                     | Storage version token.             |

The model retains two obsolete aliases: `configCorrelationId` reads and writes `id`, and `transactionType` reads and writes `name`. Use `id` and `name` in new code. These aliases do not represent separate identifiers or values.
